# OmniOutreach: Master Engineering Manual & Architectural Guide

This document is the definitive source of truth for the OmniOutreach platform. It provides a comprehensive breakdown of the system architecture, the technical stack, the Directed Acyclic Graph (DAG) execution model, and the complete database schema.

---

## 1. Executive Summary
OmniOutreach is an enterprise-grade multi-channel outreach automation platform. It is designed to orchestrate high-volume prospect engagements across LinkedIn, WhatsApp, Email, and Voice. Unlike traditional linear sequencers, Omni uses a graph-based state machine to manage complex, behavioral branching logic.

---

## 2. Core Architectural Pillars

### 2.1 The Directed Acyclic Graph (DAG) Engine
The defining feature of Omni is the transition from a linear sequence (Step 1 -> Step 2) to a nodal graph model.

- **Nodes (`sequence_nodes`)**: Represent discrete actions (Send DM, Wait, Check Reply) or start triggers. Each node stores its configuration in a flexible `JSONB` data column.
- **Edges (`sequence_edges`)**: Represent the logical flow between nodes. Edges support "handles" (e.g., a `true` handle for a reply received, a `false` handle for silence), enabling complex IF/THEN branching.
- **The Sequencer (`sequencer.py`)**: A recursive graph traversal service. It determines the next state of a lead by crawling the edges associated with the lead's current node.
- **The Dispatcher (`dispatcher.py`)**: A high-concurrency worker that executes the physical outreach (API calls, SMTP sending) based on the tasks generated by the Sequencer.

### 2.2 Concurrency & Reliability
- **Pessimistic Locking**: The task queue uses `FOR UPDATE SKIP LOCKED` logic. This ensures that multiple horizontal worker instances can safely pick up tasks without ever double-processing a lead.
- **Asynchronous Foundation**: Built entirely on Python 3.12 + FastAPI + asyncpg, the backend is optimized for non-blocking I/O, critical for handling thousands of simultaneous outreach operations.

## 3. Technical Stack Detail

### Backend (Surgical Precision)
- **FastAPI**: Serves the REST API and provides automatic OpenAPI documentation.
- **PostgreSQL**: The primary relational database, chosen for its robust support for JSONB and complex relational integrity.
- **Redis & ARQ**: Used for distributed background job processing (polling, cron tasks, and dispatcher loops).
- **Unipile API**: The unified messaging integration layer.
- **Retell AI**: Provides the voice telecaller LLM and telephony integration.

### Frontend (Mission-Critical UI)
- **React 18 + Vite**: High-performance rendering and build pipelines.
- **TypeScript**: Enforces strict data safety across the entire UI.
- **React Flow (@xyflow/react)**: The engine behind the nodal canvas, providing 60fps graph interactions and persistence logic.
- **Zustand**: Manages client-side state (auth, UI toggles) with zero boilerplate.
- **TanStack React Query**: Synchronizes the backend "Ground Truth" with the frontend UI, handling caching and automatic background refreshing.

## 4. Comprehensive Database Schema (Ground Truth)

### 4.1 Auth & Identity
- **`users`**: Master user records.
    - `id` (UUID): Primary identifier.
    - `email` (TEXT): Unique login credential.
    - `password_hash` (TEXT): PBKDF2-SHA256 hashed password.
- **`refresh_tokens`**: Manages persistent sessions and JWT rotation.

### 4.2 Messaging & Voice Accounts
- **`linkedin_accounts`**: Tracks Unipile-connected LinkedIn profiles.
    - `unipile_id` (TEXT): The unique identifier provided by Unipile.
    - `daily_invite_cap` (INT): Safety limit to prevent bans.
- **`email_accounts`**: Tracks SMTP/Resend configurations for cold email.
- **`voice_agents`**: Maps internal agents to Retell AI agent IDs.

### 4.3 Campaign & Sequence Definition (The Graph)
- **`campaigns`**: Global configuration container.
    - `sequence_mode` (TEXT): Toggles between `sequential` (linear) and `canvas` (nodal).
    - `active_hours_start/end` (INT): Defines the daily window for outreach activity.
- **`sequence_nodes`**: Nodes in the DAG.
    - `node_type` (TEXT): The functional identity (e.g., `trigger_start`, `action_email`).
    - `data` (JSONB): Dynamic configuration payload (delay days, template IDs, account IDs).
- **`sequence_edges`**: The logical wiring between nodes.
    - `source_handle` (TEXT): The logic gate (default, true, false).
- **`templates`**: The message content repository. Each template is explicitly linked to a node.

### 4.4 Lead Pipeline & Execution
- **`leads`**: The prospects currently in the system.
    - `current_node_id` (UUID): Tracks exactly where the lead is in the DAG.
    - `chat_id` (TEXT): The Unipile chat session ID for thread continuity.
    - `status` (TEXT): `active`, `stopped`, `replied`.
- **`queue`**: The pending task execution list.
    - `locked_by / locked_at`: Columns managed by the worker loop for concurrency safety.
- **`events`**: A comprehensive audit log recording every single state change and outreach action.
- **`inbound_messages`**: Raw logs of incoming replies captured via webhooks.

## 5. Sequence Execution Logic Flow

### Phase 1: Initiation
1. A lead is imported or generated via **Job Search**.
2. The **Dispatcher** assigns a LinkedIn account and queues an `action_linkedin_invite`.
3. The **ARQ worker** polls Unipile. When `network_distance` becomes `FIRST_DEGREE`, it sets `accepted_at`.
4. `sequencer.schedule_sequence()` is called. It finds the `trigger_start` node for the campaign.

### Phase 2: Traversal
1. The **Sequencer** finds all edges originating from the current node.
2. It evaluates the targets:
    - **Action Nodes**: Inserts a new row into the `queue` with the appropriate delay.
    - **Delay Nodes**: Recursively jumps to the next node after the specified interval.
    - **Condition Nodes**: Checks lead metadata (e.g., `replied_at`). If no reply, the lead parks here and `current_node_id` is updated.

### Phase 3: External Interrupts (Webhooks)
1. A prospect replies on WhatsApp.
2. Unipile sends a `message.received` event to `/webhooks/unipile`.
3. The system updates the lead's `replied_at` timestamp.
4. `sequencer.evaluate_conditions()` is triggered. It finds the lead's current "parked" node, sees the reply exists, and executes the `true` handle edge.

## 6. Integration Guide

### Unipile Pattern
All messaging (LinkedIn, WhatsApp, IG) uses the unified `/api/v1/chats` pattern. For first-touch WhatsApp, use:
- **Handle**: `[phone_number]@s.whatsapp.net`
- **Pattern**: `POST /api/v1/chats` with `attendees` and `text`.

### Retell AI Pattern
Voice nodes function by calling `POST /v2/create-phone-call`. The `retell_flow_id` is passed to ensure the call follows the specific nodal conversation flow built in the Retell dashboard.
