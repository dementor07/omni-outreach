# Omni-Outreach: Deep Dive Tutorial & Code Documentation

This tutorial covers absolutely everything regarding the architectural shift from a linear sequence builder to a Dual-Mode Multi-Channel Nodal Flow Canvas. It explains the purpose and function of every major line of code introduced during this refactor.

---

## Part 1: Database Schema Overhaul (`backend/schema.sql`)

To support branching logic, we had to move from a simple `step_order` integer to a Directed Acyclic Graph (DAG) consisting of Nodes and Edges.

### 1.1 The `campaigns` Table Update
```sql
sequence_mode TEXT NOT NULL DEFAULT 'sequential',
```
- **Explanation**: We added this column so the frontend knows whether to render the `SequentialBuilder` (linear list) or the `ReactFlow` canvas.

### 1.2 The `sequence_nodes` Table (Replaced `sequence_steps`)
```sql
CREATE TABLE IF NOT EXISTS sequence_nodes (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    campaign_id         UUID NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
    node_type           TEXT NOT NULL, 
    position_x          FLOAT NOT NULL DEFAULT 0,
    position_y          FLOAT NOT NULL DEFAULT 0,
    data                JSONB NOT NULL DEFAULT '{}',
    created_at          TIMESTAMPTZ DEFAULT NOW()
);
```
- **`node_type`**: Stores specific string identifiers used by the frontend to render the correct icon/UI (`trigger_start`, `action_linkedin_dm`, `condition_replied`, `delay`, etc.).
- **`position_x` & `position_y`**: Required by React Flow to render the node at the exact (X, Y) coordinates where the user dropped it on the canvas.
- **`data` (JSONB)**: A highly flexible column. Instead of hardcoding `delay_days` or `email_account_id` as columns, we pack all node-specific configuration into this JSON object. This allows us to add new node types in the future without altering the SQL schema.

### 1.3 The `sequence_edges` Table
```sql
CREATE TABLE IF NOT EXISTS sequence_edges (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    campaign_id         UUID NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
    source_node_id      UUID NOT NULL REFERENCES sequence_nodes(id) ON DELETE CASCADE,
    target_node_id      UUID NOT NULL REFERENCES sequence_nodes(id) ON DELETE CASCADE,
    source_handle       TEXT DEFAULT 'default',
    target_handle       TEXT DEFAULT 'default',
    created_at          TIMESTAMPTZ DEFAULT NOW()
);
```
- **`source_node_id` & `target_node_id`**: The standard way to represent a directed arrow from Node A to Node B.
- **`source_handle`**: Critical for conditional logic. If Node A is a `condition_replied` node, it has two outgoing dots (handles): one for "Replied" (handle ID `true`) and one for "No Reply" (handle ID `false`). This column tells the backend *which* path the edge belongs to.

### 1.4 The `leads` & `queue` Tables
```sql
-- In leads table:
current_node_id UUID REFERENCES sequence_nodes(id) ON DELETE SET NULL,
replied_at TIMESTAMPTZ,

-- In queue table:
node_id UUID REFERENCES sequence_nodes(id),
```
- **`current_node_id`**: Acts as a bookmark. If a lead hits a "Wait for Reply" condition node, they pause here. Their `current_node_id` is set to that node's ID until a webhook wakes them up.
- **`replied_at`**: A timestamp populated by the Unipile webhook when an inbound message is received.
- **`node_id` in `queue`**: When a task is queued for execution, we store exactly which node it belongs to, allowing the dispatcher to pull the correct templates/configurations.

## Part 2: Backend Routing & API

### 2.1 Graph Save Logic (`backend/app/routers/sequences.py`)
```python
class NodeCreate(BaseModel):
    id: str | None = None # React Flow ID (e.g., 'node_123')
    node_type: str
    position_x: float
    position_y: float
    data: dict = {}

class SequenceGraph(BaseModel):
    campaign_id: str
    nodes: List[NodeCreate]
    edges: List[EdgeCreate]
```
- **Explanation**: We define Pydantic models to accept the exact JSON structure generated by React Flow. React Flow uses temporary string IDs (like `node_12345`), but Postgres uses UUIDs.

```python
@router.post("/save")
async def save_graph(body: SequenceGraph, user_id: str = Depends(get_current_user)):
    # ... validation ...
    await execute("DELETE FROM sequence_edges WHERE campaign_id=$1", body.campaign_id)
    await execute("DELETE FROM sequence_nodes WHERE campaign_id=$1", body.campaign_id)
```
- **Explanation**: To simplify updates, we do a "Full Replace" strategy. We delete all existing edges and nodes for the campaign, then insert the new ones.

```python
    node_id_map = {} 
    for node in body.nodes:
        inserted = await fetch_one(
            "INSERT INTO sequence_nodes (...) VALUES (...) RETURNING id", ...
        )
        if node.id:
            node_id_map[node.id] = inserted["id"]
```
- **Explanation**: As we insert the nodes into Postgres, Postgres generates real UUIDs. We map the temporary React Flow ID (`node.id`) to the real UUID (`inserted["id"]`).

```python
    for edge in body.edges:
        source_id = node_id_map.get(edge.source_node_id, edge.source_node_id)
        target_id = node_id_map.get(edge.target_node_id, edge.target_node_id)
        await execute("INSERT INTO sequence_edges ...", ...)
```
- **Explanation**: When inserting edges, we look up the real Postgres UUIDs from our mapping dictionary so the foreign keys match perfectly.

### 2.2 Unipile Webhooks (`backend/app/routers/webhooks.py`)
```python
@router.post("/unipile")
async def unipile_webhook(request: Request):
    data = await request.json()
    if data.get("event") == "message.received":
        chat_id = data.get("body", {}).get("chat_id")
        lead = await fetch_one("SELECT id, campaign_id FROM leads WHERE chat_id = $1", chat_id)
```
- **Explanation**: This is the listener for Unipile. When a prospect replies on LinkedIn, WhatsApp, etc., Unipile sends a POST request here. We extract the `chat_id` and query our DB to figure out which `lead` this belongs to.

```python
        if lead:
            await execute("UPDATE leads SET replied_at = NOW(), status = 'replied' WHERE id = $1", lead["id"])
            await sequencer.evaluate_conditions(str(lead["id"]))
```
- **Explanation**: We mark the exact time the reply came in. Then, we call `evaluate_conditions()`. If this lead was "sleeping" at a Condition node, this function will wake them up and push them down the "True" branch.

## Part 3: The Execution Engine (Sequencer & Dispatcher)

### 3.1 Graph Traversal (`backend/app/services/sequencer.py`)
```python
async def schedule_sequence(lead_id: str) -> None:
    start_node = await fetch_one(
        "SELECT id FROM sequence_nodes WHERE campaign_id=$1 AND node_type='trigger_start' LIMIT 1",
        lead["campaign_id"]
    )
    await queue_next_nodes(lead_id, start_node["id"])
```
- **Explanation**: When a lead accepts an invite, we don't just look for "step 1". We explicitly query for the `trigger_start` node (the genesis block of our DAG) and pass it to our recursive graph crawler.

```python
async def queue_next_nodes(lead_id: str, source_node_id: str, handle: str = "default") -> None:
    edges = await fetch_all(
        "SELECT target_node_id FROM sequence_edges WHERE source_node_id=$1 AND source_handle=$2",
        source_node_id, handle
    )
```
- **Explanation**: This is the heart of the DAG logic. We ask the DB: "For the node we just finished, what edges point outward from it using the specified handle?" (Normally 'default', but could be 'true'/'false').

```python
    for edge in edges:
        target_id = edge["target_node_id"]
        node = await fetch_one("SELECT * FROM sequence_nodes WHERE id=$1", target_id)
        
        if node["node_type"].startswith("action_"):
            # Put the action into the queue table so the dispatcher can execute it
            await execute("INSERT INTO queue ... VALUES ...", ...)
            
        elif node["node_type"] == "delay":
            # Pass through the delay node recursively
            await queue_next_nodes(lead_id, target_id)
            
        elif node["node_type"] == "condition_replied":
            if lead["replied_at"]:
                # If they already replied in the past, skip waiting and immediately go down the 'true' branch
                await queue_next_nodes(lead_id, target_id, "true")
            else:
                # Pause execution. Bookmark this lead's location.
                await execute("UPDATE leads SET current_node_id=$1 WHERE id=$2", target_id, lead_id)
```
- **Explanation**: The sequencer iterates over all target nodes and handles them based on type. Actions get queued for actual network requests. Conditions either evaluate instantly or pause the lead.

## Part 4: Frontend State & UI

### 4.1 State Management (`frontend/src/hooks/useSequenceSteps.ts`)
```typescript
export function useGetGraph(campaignId?: string) {
  return useQuery({
    queryKey: ['sequence-graph', campaignId],
    queryFn: async () => {
      const { data } = await api.get<{ nodes: SequenceNode[]; edges: SequenceEdge[] }>(`/sequences/${campaignId}`)
      return data
    },
  })
}
```
- **Explanation**: We use TanStack React Query to fetch the entire graph (nodes and edges) in one shot. This powers both the Canvas and the Sequential Builder.

### 4.2 The Linear UI Compiler (`frontend/src/components/SequentialBuilder.tsx`)
```tsx
export default function SequentialBuilder({ nodes, edges, onSave }: Props) {
  const steps = React.useMemo(() => {
    return nodes
      .filter(n => n.type !== 'trigger_start')
      .map(n => ({
        id: n.id,
        type: n.type as NodeType,
        delay_days: n.data?.delay_days || 0
      }))
  }, [nodes])
```
- **Explanation**: The Sequential Builder doesn't care about edges for *display*. It just strips out the `trigger_start` node and lists the rest in array order. (In a perfect robust implementation, this would sort based on topological order of the edges, but this suffices for simple linear creation).

```tsx
  const addStep = (type: NodeType) => {
    const newId = `node_${Date.now()}`
    const lastNode = nodes.length > 0 ? nodes[nodes.length - 1] : null
    
    const newNode: Node = { id: newId, type, position: { x: 250, y: nodes.length * 150 + 100 }, data: { ... } }
    const newEdges = [...edges]

    if (lastNode) {
      newEdges.push({
        id: `edge_${lastNode.id}_${newId}`, source: lastNode.id, target: newId, sourceHandle: 'default', targetHandle: 'default'
      })
    }
    onSave([...nodes, newNode], newEdges)
  }
```
- **Explanation**: The magic trick. When a user clicks "Add Step" in the linear UI, we generate a React Flow `Node` object. We look at what the *previous* node was, and we automatically generate an `Edge` connecting the previous node to this new node. We then pass these fully-formed graph objects up to `onSave()`. The backend never knows this was created in a linear list.
